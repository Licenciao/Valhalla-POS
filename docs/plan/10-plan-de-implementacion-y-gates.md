# Plan de implementación y gates de calidad

## Estado y alcance

Este documento organiza la implementación de `09-pseudocodigo.md`. El responsable aprobó explícitamente el diseño técnico y los casos de prueba de P-03; P-04/P-05 quedan autorizados para codificación en `apps/api` y `apps/clients`.

La aprobación del pseudocódigo confirma reglas funcionales, pero no sustituye la aprobación del diseño de implementación. No se declarará seguridad absoluta ni se aprobará un incremento sin evidencia verificable del alcance probado.

## Arquitectura confirmada

- Flutter/Dart para Android y Windows; Android 12/API 31 como mínimo y la última versión GA de Windows 11 con soporte vigente al desplegar. La PC tendrá Windows 11 Home. Referencia vigente al 9 de noviembre de 2026: 26H2; revalidar antes del despliegue.
- La PC Windows aloja Django REST Framework y PostgreSQL. PostgreSQL es la autoridad central y no acepta conexiones de clientes; la API `/api/v1` es la única frontera de escritura.
- La aplicación Windows se distribuye como MSI construido con WiX Toolset; los datos PostgreSQL permanecen fuera del directorio reemplazable. Firewall permite API TCP 8443 en perfil privado y LAN; PostgreSQL escucha solo localmente.
- La API está disponible solo mientras la aplicación Windows está abierta. La red de clientes es LAN/Wi-Fi con HTTPS y huella de certificado emparejada por QR de un solo uso. ADMIN usa Django Auth mediante cookie de sesión y CSRF en Windows.
- Cada Android usa una clave exclusiva ECDSA P-256/SHA-256 en Android Keystore; el servidor conserva SPKI DER/Base64URL y deriva `key_id` con SHA-256 de esos bytes. Las solicitudes firman protocolo, instancia, `key_id`, método, ruta de segmentos ASCII/UUID y query vacía, hash SHA-256 del cuerpo exacto, timestamp y nonce; representación UTF-8 en orden fijo separado por LF y firma DER/Base64URL sin padding. Endpoints Android firmados no usan query; el cursor de paginación, si aplica, va en la ruta. Timestamp ±5 minutos y nonce aleatorio de 128 bits consumido atómicamente/retenido 15 minutos. El QR es de un uso por 5 minutos y contiene endpoint LAN, instancia, huella TLS y token aleatorio de 256 bits; Windows almacena solo SHA-256 y consume atómicamente. El administrador inicia el alta y el primer escaneo válido la completa. La clave no expira automáticamente; revocación/reemplazo requiere decisión administrativa. Nuevo emparejamiento genera clave nueva; identidad/secuencia solo se conservan si el administrador confirma que es el mismo equipo, mientras que uno perdido recibe identidad nueva. Renovar la huella TLS requiere nuevo emparejamiento QR. Si se pierde la respuesta de alta, mismo `pairing_request_id`/QR/clave pública devuelve el resultado persistido sin duplicar; diferencia requiere nuevo QR.
- `/api/v1` conserva compatibilidad para cambios aditivos; cambios incompatibles requieren ruta mayor nueva. El servidor informa incompatibilidad y no descarta eventos pendientes.
- Toda escritura Windows distinta de login/logout usa `Idempotency-Key` UUID; los eventos Android usan su UUID de evento y las repeticiones no duplican efectos.
- Android opera offline con SQLite cifrado, cuotas y outbox UUID/secuencia. Retiene los eventos hasta ACK; un conflicto conserva el payload y detiene la cola.
- Windows mantiene una caché SQLite cifrada de solo lectura y no tiene outbox. Si API/PostgreSQL no está disponible, permite lecturas desde caché íntegra con aviso de posible obsolescencia; si es inválida, muestra error. Sus escrituras requieren respuesta satisfactoria de la API y nunca se encolan.
- Instalador Windows, con datos PostgreSQL fuera del directorio reemplazable de la aplicación.
- Respaldo cifrado diario a Drive a las 22:00 UTC-06:00 mientras la aplicación Windows está abierta. Si se pierde esa ejecución, queda pendiente hasta el siguiente inicio de la aplicación. Cualquier fallo de dump, cifrado, carga o verificación conserva una copia local válida, deja el estado pendiente/error visible y reintenta en la siguiente ejecución diaria. Drive conserva 30 días; no eliminar la copia local antes de verificar la carga. Tras verificar, conservar la copia local válida más reciente y las siete anteriores. Antes del primer respaldo válido, exigir espacio libre de al menos 2× la estimación basada en el tamaño actual de PostgreSQL; alertar y no borrar copias si es insuficiente. Restauración aislada mensual y después de cambios importantes de instalación o esquema. El segundo custodio del secreto se designa antes de activar respaldos.
- Para considerar una carga verificada, validar finalización/integridad de dump y cifrado y comparar tamaño y SHA-256 remoto/local; si Drive no expone hash, descargar el objeto y calcularlo. Cualquier fallo deja la copia local conservada y el estado pendiente/error.

## Flujo y responsabilidades por cliente

| Operación | Android | Windows |
|---|---|---|
| Lecturas | Usar datos sincronizados en SQLite y mostrar estado/antigüedad. | Consultar API y mantener caché de lectura; si falla API/PostgreSQL, permitir lectura solo de caché íntegra con aviso de posible obsolescencia; caché inválida produce error. |
| Venta | Validar cuota y costo; una solicitud insuficiente queda local, sin reserva. Un surtido válido descuenta cuota y crea evento en una transacción local; permanece pendiente hasta ACK. | Enviar a API; el servidor valida stock central no asignado y aplica operación/movimientos de forma atómica. Confirmar solo tras respuesta satisfactoria. |
| Entrada | Guardar localmente y encolar; al aplicar, aumenta stock central no asignado, sin asignar cuota automáticamente. | Enviar a API y confirmar solo tras respuesta satisfactoria. |
| Devolución | Validar venta/dispositivo, componentes completos y reembolso; aplicar cuota local y encolar hasta ACK. | Enviar a API; confirmar solo tras aplicar la transacción central. |
| API no disponible | Conservar operaciones permitidas dentro de la cuota; no presentar como sincronizadas. | Mostrar error explícito; no escribir en la caché ni crear outbox. |
| Conflicto | Conservar el evento original y pausar la cola hasta resolución/ACK. Aceptación aplica operación, consume secuencia y guarda ACK atómicamente; rechazo consume secuencia sin operación oficial y genera ACK terminal. Retirar de la cola activa solo tras ACK y conservar historial. | Mostrar resultado central; resolución administrativa por API y auditada. Aceptación y secuencia/ACK son atómicos; rechazo no oficial consume secuencia mediante ACK terminal. |

Las operaciones centrales que compiten por stock deben serializarse o protegerse con controles transaccionales equivalentes para que no se confirme una sobreventa. La técnica concreta se define en el diseño de P-03.

### Primer incremento aprobado P-04/P-05

- **P-04 / Programador:** base Django REST Framework en `apps/api`; endpoints de health, CSRF y sesión, sobre común de errores, `SystemInstance` singleton persistido y aprovisionamiento por comandos locales. PostgreSQL es requisito de ejecución; pruebas pueden usar base aislada siempre que no se confunda con la autoridad de producción.
- **P-05 / Programador:** base Flutter Android/Windows en `apps/clients`; shell de conexión/login para Windows, preparación del proyecto multiplataforma y pruebas del estado de health/login. No implementa operaciones ni datos de inventario todavía.
- **Toolchain aprobada:** Python `>=3.12`, desarrollo/pruebas en Python 3.13 (actualmente 3.13.18); 3.15 no se certifica hasta validación. Flutter stable 3.47.9 está instalado en el perfil de usuario y el archivo se verificó contra el SHA-256 oficial. Este entorno aún no tiene Visual Studio con Desktop C++ ni Android SDK; por ahora se ejecutan análisis y pruebas Flutter, no compilaciones nativas.
- **QA:** verificar Q-18, Q-21–Q-24 y CA-32, CA-37–CA-40 aplicables a este incremento; probar que PostgreSQL no disponible produce `503 SERVICE_UNAVAILABLE`, que el `instance_id` persiste y que ADMIN/OPERADOR se derivan de las reglas aprobadas.
- **Fuera de alcance:** catálogo, movimientos, ventas, costos, outbox, sincronización firmada, claves Android y respaldo. No usar ni oficializar datos de inventario inicial no conciliados.
